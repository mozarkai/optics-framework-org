Create it your way. Run it forever.

Optics is open-source test automation for Android, iOS, web and TV. Write a test by hand, record it, describe it in plain English or hand it to your AI agent, then run that same suite on every build and every device.

$ curl -fsSL https://optics-framework.org/install | sh
Get started View on GitHub

Apache 2.0. Needs Python 3.12 or newer. Windows and pip

Every test has two lives.

The day you create it

Someone turns a user flow into steps a machine can repeat. Optics lets that person work the way they already think: in a spreadsheet, on the device, in a sentence, or through an AI agent.

Every day after that

The test has one job: run the same way on every build, every device and every release, and fail only when the app is actually broken.

Four ways to create a test

Click a bracket of the logo or pick from the list.

Write it

Elements, modules and test cases are plain CSV or YAML that anyone on the team can read and review. Prefer code? The same keywords are a Python library and a Robot Framework library.

Record it

Open optics live next to your device and run keywords one at a time. Every step that works is recorded, and /save writes the recording into your suite as a reusable module.

Say it

Press Ctrl N in optics live and describe the flow. An AI agent drives the device a step at a time, then keeps only the steps that mattered, ready to save. Uses the Gemini model you configure.

Delegate it

Add optics mcp to any MCP client. Every keyword becomes a tool and the screen becomes a resource, so your agent can explore the app and write the suite files itself. The agent is yours; Optics gives it eyes and hands.

Every way ends in plain text

Reviewed like code

A recording in Optics isn't a binary blob or a row in someone else's cloud. /save writes the same rows you would have typed, and an agent working through optics mcp writes them too. They live in your repo, next to the app they test.

So changing a test is a pull request. When a redesign moves the sign-in button, the diff shows the one locator that changed and the text fallback added beside it, and CI runs exactly what was merged.

CSV or YAML

Write in whichever your team reads best. CSV opens in any spreadsheet and keeps one step per row. YAML keeps a whole flow in one indented file. /save writes either, and one project can hold both.

Optics tells files apart by what is inside them, not where they sit, so the folder layout is yours. Both formats load into the same suite, and each file holds one of three things.

Test cases
Which flows run, and in what order.
Modules
The steps, one keyword each, reused by every test case that names them.
Elements
Every name mapped to the ways to find it on screen. The only place a locator lives, so a redesign is an edit here and not in every test.

Run a suite

optics execute replays the suite step by step. Check it first without a device using optics dry_run, which validates every keyword, element and module reference.

junit_output.xml
Written as the run goes, so CI sees progress live.
Screenshots
Before and after every action, annotated with the strategy that found the element.
Detected errors
Crash dialogs and messages like “Session expired”, matched from error_definitions.csv, fail the run even without an assertion.

How Optics finds an element

Most frameworks give an element one locator and fail when a redesign changes it. Optics gives every element several identities and tries them in order, cheapest first, so vision only costs you time when the UI tree can't help.

Two more fallbacks sit alongside the ladder. List several values for the same element name and each is tried in turn. Enable a second driver or element source and it takes over when the first one fails.

  1. 1
    XPathA native query through the accessibility tree.
  2. 2
    TextThe visible text, CSS or class in the page source.
  3. 3
    OCRReads the screenshot with EasyOCR, Tesseract or Google Vision.
  4. 4
    ImageMatches a reference picture of the element on screen.
  5. 5
    AI self-heal, if you switch it onAn LLM reads the screen and recovers with the same keywords, in optics live and optics execute.

Where suites run

On every build

Run in CI and read results as they arrive. On-screen error detection fails the build when the app crashes mid-test, even if no assertion would have caught it.

Before every release

Run the full regression on your own emulator or device, with annotated screenshots of every step to show exactly what the test saw.

On every device

Android, iOS, Android TV, Samsung Tizen and LG webOS through Appium. Web through Selenium or Playwright. The keywords stay the same.

In production

Point the same suite at your live app on a schedule. Where debugging and screenshots are locked down, the BLE driver acts as a Bluetooth mouse and keyboard, paired with a camera.

Install

  1. 1Install Optics

    The installer keeps Optics in its own environment under ~/.optics, away from your system Python.

    $ curl -fsSL https://optics-framework.org/install | sh
    > irm https://optics-framework.org/install.ps1 | iex
    $ pip install optics-framework

  2. 2Set up a project

    Asks what you want to automate, installs the matching driver and OCR engine, scaffolds a project from a working sample and checks your setup. Add more engines any time with optics setup.

    $ optics quickstart

  3. 3Run it

    Then run it again on the next build, and every one after that.

    $ optics execute my_test_project
