Optics in one minute.

Every test has two lives.

The day you create it

Someone has to turn a user flow into steps a machine can repeat. Optics lets that person work the way they already think: in a spreadsheet, on the device, in a sentence, or through an AI agent.

And every day it runs

After that, the test has one job: run the same way on every build, every device and every release, and fail loudly only when the app is actually broken.

Pick your way in.

Whoever writes the test, there is a way that fits how they already work. Click a bracket of the logo, or pick from the list.

Write it as data.

Elements, modules and test cases are plain CSV or YAML that anyone on the team can read and review. Prefer code? The same keywords are a Python library and a Robot Framework library.

Record it by using the app.

Open optics live next to your device and run keywords one at a time. Every step that works is recorded, and /save writes the recording into your suite as a reusable module.

Say it in plain English.

Press Ctrl N in optics live and describe the flow. An AI agent drives the device a step at a time, then keeps only the steps that mattered, ready to save. Uses the Gemini model you configure.

Delegate it to your agent.

Add optics mcp to any MCP client. Every keyword becomes a tool and the screen becomes a resource, so your agent can explore the app and write the suite files itself. The agent is yours; Optics gives it eyes and hands.

Four ways in, one suite.

However a test starts, it ends up as the same few files. Commit them, review them in a pull request, and run them anywhere. Optics recognises each file by what's in it, so the folder names are only a convention.

One command, every time.

One command replays the suite step by step. Results stream into junit_output.xml as the run goes, so your CI sees progress live, with a screenshot of every action.

Check a suite before you have a device: optics dry_run validates every keyword, element and module reference.

When the app changes, Optics looks again.

Most frameworks give an element one locator and fail the moment a redesign changes it. Optics gives every element several identities and tries them in order, cheapest first. Vision only costs you time when the UI tree can't help.

List more than one value for the same element name and those are tried too. Enable a second driver and it becomes a fallback.

  1. 1
    XPathA native query through the accessibility tree.
  2. 2
    TextThe visible text, CSS or class in the page source.
  3. 3
    OCRReads the screenshot with EasyOCR, Tesseract or Google Vision.
  4. 4
    ImageMatches a reference picture of the element on screen.
  5. 5
    AI self-heal, if you switch it onAn LLM reads the screen and recovers with the same keywords, so it re-enters the ladder instead of tapping blind. Works in optics live and optics execute.

Same suite, everywhere it matters.

On every build

Run in CI and read results as they arrive. Add an error_definitions.csv and Optics also watches the screen for crash dialogs and error messages, failing the build even when no assertion would have caught it.

Before every release

Run the full regression on your own emulator or device, with annotated screenshots of every step to show what the test saw.

On every device

Android, iOS, Android TV, Samsung Tizen and LG webOS through Appium. Web through Selenium or Playwright. The keywords don't change.

Around the clock

Point the same suite at your production app on a schedule. On devices where debugging and screenshots are locked down, the BLE driver acts as a Bluetooth mouse and keyboard, paired with a camera.

Get to a running test in three commands.

  1. Install

    $ curl -fsSL https://optics-framework.org/install | sh
    > irm https://optics-framework.org/install.ps1 | iex
    $ pip install "optics-framework[appium,easyocr]"

    The installer keeps Optics in its own environment under ~/.optics, away from your system Python.

  2. Set up a project

    $ optics quickstart

    Asks what you want to automate, installs the right engine, scaffolds a project from a working sample and checks your setup. Pressing Enter throughout still gives you a runnable project.

  3. Run it

    $ optics execute my_test_project

    Then do it again tomorrow, and on every build after that.
