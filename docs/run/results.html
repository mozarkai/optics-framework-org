Docs/Run and report

Read the results

Find out what happened in a run from the JUnit report, the screenshots and the logs.

Beginner6 min
View as Markdown

Every run writes its results to execution_output/ inside the project folder. The terminal tree tells you what failed. The files tell you why.

What a run writes#

FileWhen it's writtenUse it to
junit_output.xmlEvery runShow results in CI. Standard JUnit XML that GitHub Actions, GitLab, Jenkins and others read.
…pre_<keyword>.jpgBefore each step that finds an elementSee what was on screen when the step started.
…_detection_result.jpgWhen Optics found an element by positionSee exactly what Optics found, boxed in green.
…_with_aoi.jpgWhen a step uses an area of interestCheck the area covers the right part of the screen. It's drawn in blue.
…end_of_run.jpgAt the end of the runSee where the app was left.
page_sources_log.xml or .htmlWhen the UI tree is readFind the right XPath or text for an element.
internal_logs.log, execution_logs.logWith file_log: trueRead every attempt Optics made, including which ways of finding an element failed.
logs.jsonWith json_log: trueFeed results into your own dashboards.
detected_errors_<id>.jsonWhen an error screen was foundSee which error definition matched.

Investigate a failure#

  1. Read the Failure details box in the terminal. It names the test case, the step and the reason.
  2. **Open the last pre_… screenshot** before the failure. Is the screen what you expected? If it shows a loading spinner, the step ran too early: add an Assert Presence before it. If it shows a different screen, an earlier step went somewhere unexpected.
  3. Search the logs for the element's value. With file_log: true, execution_logs.log has a line for every attempt, such as Trying … on 'Sign in' ... FAIL.
  4. **Reproduce it in optics live.** Run the steps before the failure, then try the failing step with different values until one works. See Record a test.

Add these to config.yaml:

log_level takes DEBUG, INFO (the default), WARNING or ERROR. Use WARNING to keep the terminal quiet so the tree stands out.

Read the JUnit report#

junit_output.xml has one <testcase> per test case, with a <failure> when it failed. Inside each, Optics records every module and keyword with its status and timing, so CI tools that show nested steps display the same tree you saw in the terminal.

If error screens were detected, the report has an extra failing test case called on-screen-error-detection. See Catch error screens.

Keep the folder tidy#

Screenshots from every run accumulate in execution_output/. Clear the folder before runs where you need clean results, such as in CI:

To write results somewhere else, set execution_output_path in config.yaml. A relative path is relative to the folder you run optics from, and the folder must exist.
