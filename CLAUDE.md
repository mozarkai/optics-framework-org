# optics-framework.org

Static landing page and documentation for Optics. No framework, no dependencies.

- `site/` is the page: `index.html`, `styles.css`, `app.js`, `logo.svg`, `fonts/`, `media/`, plus the machine-readable files copied as-is: `index.md` (the homepage as Markdown), `404.md`, `llms.txt`, `robots.txt` and `openapi.json`. Keep `index.md` and `llms.txt` in step with `index.html` when the copy changes.
- `site/openapi.json` is the `optics serve` API, generated rather than hand-written. After an optics-framework release, check out its tag and run `<checkout>/.venv/bin/python scripts/openapi.py <checkout>` to refresh it. The script adds the local `servers` entry and the description saying the API is not hosted here.
- `site/doors-contract.js` feeds the "doors" under the `optics live` playground (`site/doors.js`): each step the visitor runs, shown as CSV, Python, Robot, HTTP and MCP. Refresh it from the same tag with `<checkout>/.venv/bin/python scripts/doors.py <checkout>` (needs Playwright's Chromium). It reads the keyword, HTTP and MCP contracts from the source and records real replies from one session per interface against `scripts/doors-fixture/`. `test/doors.test.mjs` fails when a snippet stops matching the contract.
- `lib/footer.mjs` builds the footer every page shares (the homepage, `pages/_layout.html`, `docs/_layout.html` and the 404): the latest release and four link columns. Change links there, not in a layout.
- `pages/` holds the text pages (`about`, `contact`, `privacy`, `404`) as body fragments; `build.mjs` wraps each in `pages/_layout.html` and writes `out/<name>.html`, which GitHub Pages serves at `/<name>`. Add a page by adding its fragment and an entry to `PAGES` in `build.mjs`; it lands in `sitemap.xml` automatically, with `lastmod` taken from the fragment's last commit.
- `site/agents.md` is the setup procedure an agent follows when a person pastes the homepage prompt (`#agents`): find or install Optics, register the MCP server, check it with a headless browser, then test a web app, a phone app or CI. Every step checks before it changes something, so it is safe to follow again, and it asks the person only for a device, credentials, a `sudo` command or a client restart. Keep the four prompts in `site/index.html` and `site/index.md` the same; a test checks it.
- `site/.well-known/` holds the agent discovery files: `api-catalog` (RFC 9727; the worker gives it its media type), `ai-catalog.json`, `mcp/server-card.json` and one `agent-skills/<name>/SKILL.md` per skill. The build writes `agent-skills/index.json` with each file's digest. Bump the server card's `version` with each optics-framework release, alongside `openapi.json`.
- `site/release.json` holds one headline and docs link per optics-framework release. Optics shows the newest one when an update is available, and the one for the installed version on its first run after an upgrade. Add the new release's entry when you release; a release without one still gets the update notice, with no headline.
- `public/install.sh` and `public/install.ps1` are the installers served at `/install`, `/install.sh` and `/install.ps1`. Their CI lives in `.github/workflows/test-installer.yml`.
- Birch is a real web app: `site/birch/` with `site/birch-app.js` and `site/birch-app.css`; `?release=2.2` shows "Session expired" at checkout. `site/birch-tests/` is the Optics suite for it. `site/runs/` is generated, so never edit it by hand: after an optics-framework release, run `<checkout>/.venv/bin/python scripts/birch-run.py` (or the "Rerun the Birch suite" workflow). `/run` (`site/replay.js`) reads `site/runs/birch-run.js`; `lib/run.mjs` builds `/run` and the homepage's two-release card (`<!-- run:card -->`) from it.
- The Playground nav item opens a row of tabs (`lib/play.mjs`): `/playground`, `/popups`, `/run`, `/ship` (break the test and the release simulator), `/hard-targets` (the wild scenes) and `/explain`. `build.mjs` puts the row at the top of each. A new playground goes in `PLAY_TABS` and, if it is a plain fragment, in `PLAY_PAGES` with its Markdown twin beside it in `pages/`. Old homepage `?sim=` links, and old `/releases?sim=` links, forward to `/ship`.
- `/popups` (`pages/popups.html`, `site/popups.js`, `site/popups.css`) runs the same engine as `/playground` with popup rules. `site/popups.js` sets `window.OPTICS_LAB` before `site/engine.js` loads: the project files and a layer that draws the popups into Birch's page source as Android dialogs. The Birch driver's `popup_screen` hands that source to Optics' own `AppiumScreen`. Popup text must not contain a suite target (`Trail`, `10`, `Add to cart`, `OK`): Birch's text lookup also accepts a substring. Spin to win comes back after exactly two page-source reads, so check the Clingy scenario still ends in E0407 after an engine bump. `pages/popups.html` and `pages/popups.md` name the optics-framework version: change it with `pages/playground.*` on each release.
- `/explain` (`pages/explain.html`, `site/explain.js`) explains a pasted suite row by row from `content/explain/catalogue.json`; `test/fixtures/explain/goldens.json` holds what real `optics dry_run` says, and a test fails when the page's prediction drifts. After an optics-framework release, run `<checkout>/.venv/bin/python scripts/explain.py <checkout>`.
- `scripts/readme-art.py <checkout>` records the hero and the four playgrounds (`/playground`, the homepage simulator, `/run`, `/explain`) as looping light and dark WebP files in `<checkout>/.github/assets/readme/`, which the optics-framework README shows. It needs `npm run dev` and `img2webp`. Rerun it after a playground changes its look.
- `/playground` runs the real optics package in the browser on Pyodide (`site/engine.js`, about 30 MB, loaded on demand). `lib/engine.mjs` downloads the files pinned with digests in `lib/engine-lock.json` into a cache outside the repo (`ENGINE_CACHE`); bump the pins after a release.
- `npm run build` copies both into `out/` and builds the docs (see below); `.github/workflows/deploy.yml` runs `npm test`, then publishes `out/` to GitHub Pages (`main` → `/`, any other branch → `/<branch>/`). The build also fingerprints `styles.css`, `app.js` and every `media/` file linked from each page (`?v=<content hash>`), including `docs.css`, `docs.js`, `scenes.js` and `scene-defs.js` on docs pages, so link them without a query string.
- Keep every URL in `site/` and `pages/` relative so branch previews work. The one exception is `404.html`: Pages serves it for a missing path at any depth, so its assets use `{{root}}`, the deploy's base path.
- Themes: tokens live under `[data-theme="light"]` and `[data-theme="dark"]` in `styles.css`; the inline script in `<head>` picks one before first paint.
- Local preview: `npm run dev` then open http://localhost:4173. It serves `out/` the way Pages does (`/about` → `about.html`, missing paths → `404.html`) through the edge worker, so `curl -H 'Accept: text/markdown' http://localhost:4173/` shows what agents get.
- Tests: `npm test` (builds, then `node --test`).

## Numbers on the homepage (`content/proof.json`)

The "Built in the open" band (`#proof`) shows PyPI downloads, GitHub stars and the latest release, each with its source and date. `/releases` (`lib/releases.mjs`, with its `.md` twin) lists every published release from the same file, grouped by minor version; a release's headline comes from `site/release.json` when it has one. `npm run proof` (`scripts/proof.mjs`) reads them from the public PyPI download logs (via ClickPy) and the GitHub API and writes `content/proof.json`; commit the file. The build renders it into `site/index.html` and `site/index.md` at the `<!-- proof -->` marker through `lib/proof.mjs` and never goes online. The headline counts only downloads by the tools in `REAL_INSTALLERS` (`edge/snapshot.js`); mirrors, browsers and unnamed clients are shown apart under "Sources and method". A release's lines are its `feat` pull request titles. Refresh after each release.

## Blog (`content/blog.json`)

`/blog` lists articles, videos and posts. Articles we write are hosted here at `/blog/<slug>` and are the canonical copy: copies on Medium, dev.to and Hashnode set their canonical URL to the page here, and translations link to it. Items published elsewhere (YouTube, LinkedIn, X, Instagram, other authors) link out to the original. `lib/blog.mjs` turns `content/blog.json` into `out/blog.html`, its Markdown twin `out/blog.md`, the RSS feed `out/feed.xml`, the "From the blog" band on the homepage (filled in at the `<!-- blog:latest -->` marker in `site/index.html` and `site/index.md`; the band disappears when there are no items), and for each hosted article `out/blog/<slug>.html` plus `out/blog/<slug>.md`, both listed in `sitemap.xml`.

- A hosted article is an item with a `slug` (lowercase words joined by hyphens) and no `platform` or `url`; its body is `content/blog/<slug>.md`, rendered by `lib/markdown.mjs` like a docs page. Start the body at the first paragraph: the title, summary, date, author and hero image come from `content/blog.json`. Use `##` for sections, site paths like `/media/blog/x.webp` and `/docs/run/ci` for images and links (they become relative in HTML and absolute in the Markdown twin), and an italic paragraph right after an image for its caption. Turn a long screen recording into a muted looping MP4 (`<video src="../media/blog/x.mp4" poster="../media/blog/x-poster.webp" autoplay loop muted playsinline preload="none" aria-label="…">`); an 8 MB GIF became 1 MB. Short GIFs go in as animated WebP (`gif2webp -mixed -q 75 -m 4`).
- Add an item to `items` (any order; the build sorts by date): `type` (`article`, `video` or `post`), `platform` (`medium`, `youtube`, `linkedin`, `x`, `instagram`, `github`; a new platform needs a mark in `PLATFORMS`), `title`, `summary`, `url`, `date` (YYYY-MM-DD), and optionally `author` and `length` ("5 min read", or "9:42" for a video). Articles and videos need an `image`. Items can be from any account; there are no per-account channels, and `author` records who wrote it.
- Save thumbnails to `site/media/blog/` as WebP, about 1280 px wide (`cwebp -q 82`), and never hot-link them: the privacy page promises the site loads nothing from other servers, and a test enforces it. For a YouTube video, download `https://i.ytimg.com/vi/<id>/maxresdefault.jpg` once and convert it. Videos link out to YouTube; there are no embedded players for the same reason. Posts on LinkedIn, X or Instagram need no image; their summary is shown as a quote.
- The newest item is the wide lead card. Type filters appear on `/blog` once there is more than one type, and `/blog?type=video` opens on a filter. Discovery beyond the feed is via RSS (`/feed.xml`).

## Documentation (`docs/`)

The docs live at `/docs/` and are built from Markdown by `lib/docs.mjs` and `lib/markdown.mjs`, a small renderer written for this site.

- `docs/nav.json` is the table of contents: sections (the tabs across the top) with groups of page ids. A page id is its path under `docs/` without `.md`; `x/index` is the landing page of section `x`. Add a page by writing its `.md` file and listing its id here; it lands in the sidebar, pager, search, `sitemap.xml`, `docs/llms.txt` and the tests automatically.
- Each page starts with front matter: `title`, `summary` (the one-sentence subtitle), and optionally `nav` (shorter sidebar label), `level` (Beginner, Intermediate, Advanced), `time` and `layout: wide`.
- Beyond plain Markdown, pages use directives: `:::note` / `:::tip` / `:::warning` / `:::mistake` / `:::important` callouts, `:::steps` (each `###` is a numbered step), `:::tabs{group="os"}` with `::tab[Label]` lines (synced and remembered per group), `:::cards{cols="2"}` link cards, `:::details[Summary]`, `- [ ]` checklists and `::scene{name="…" caption="…"}` animated figures. See the comment at the top of `lib/markdown.mjs`.
- Link other docs pages as `/docs/section/page` (or `/docs/section/` for a landing page); the build rewrites them to relative URLs and fails on a link to a page that does not exist. Tests also check every link and `#anchor`.
- Every page is also written as `out/docs/<id>.md`, a plain-Markdown twin for agents, and `docs/_layout.html` wraps the HTML.
- `site/docs.css` and `site/docs.js` style the docs and run the sidebar drawer, tabs, copy buttons, "On this page" and search (`out/docs/search.json`). `site/scenes.js` is the animation engine (a timeline, a Birch shop phone, terminals, files and wires), and `site/scene-defs.js` holds the scenes themselves. Scenes play only while visible, loop, pause on request and show their final frame when the visitor prefers reduced motion.
- Write in the voice of the existing pages: second person, short sentences, verb-led task titles. Internals (layers, classes, module paths, design decisions) go only in the Contribute section (`docs/contribute/`), which took over the framework repo's old architecture and contribution pages; every other section stays free of them. The docs describe Optics as released; flag version-specific bugs with a `:::mistake` callout that says what to do until the fix ships.
- Diagrams are ```` ```mermaid title="…" ```` fences; the title is required and shows in the frame's header. The build never draws them: `node scripts/diagrams.mjs` renders each new or changed fence once into `content/diagrams/<hash>.svg` (pinned mermaid-cli through `npx`, Playwright's Chromium), with the site's tokens in place of colours so one file works in both themes. Commit the SVGs. The build inlines them, fails on a fence with no SVG, and the Markdown twin keeps the Mermaid source. `--redraw` draws them all again after a theme change. A light runs along the lines once on screen and on hover; it stays still on phones and under reduced motion.
- The Contribute pages stay out of `llms-full.txt` (it is for people using Optics) but are listed in `docs/llms.txt`.

## Markdown for agents (`edge/`)

GitHub Pages cannot vary a response on the `Accept` header, so `edge/worker.js` is a Cloudflare Worker meant to sit in front of it on `optics-framework.org/*`. A request preferring `text/markdown` gets the page's `.md` twin (`/` → `/index.md`), or `/404.md` with a 404 for a missing page; a request preferring JSON gets a missing page as an RFC 9457 `application/problem+json` document. Both carry `Vary: Accept`; everything else passes through, with `Vary: Accept` and the discovery `Link` header added to HTML. It only takes effect once the domain is proxied through Cloudflare and the worker is deployed (`npx wrangler deploy` from `edge/`). Until then, agents can still fetch `/index.md` and `/llms.txt` directly.

## Analytics (`edge/analytics.js`, `site/track.js`, D1)

First-party only: nothing loads from another server, no cookies, no IP addresses. The worker writes one `hits` row per request it answers (assets that loaded are skipped), with the client sorted by `edge/agents.js` into `optics` (the Optics CLI or MCP server fetching `/release.json`, with its version, surface and OS), `browser`, `ai-user` (an assistant fetching for a person), `ai-crawler`, `search`, `script`, `bot` or `prefetch`. `site/track.js`, loaded on every page, posts interaction events to `POST /e` with a per-tab visit id; the worker checks each batch and writes `events` rows. A daily cron (`edge/snapshot.js`) upserts PyPI downloads (public ClickHouse dataset) and GitHub counters into `pypi` and `github`; GitHub traffic needs a `GITHUB_TOKEN` worker secret, and `npm run stats` collects it through your own `gh` login instead.

- The store is the D1 database `optics-analytics` (schema in `edge/migrations/`, applied with `npx wrangler d1 migrations apply optics-analytics --remote` from `edge/`).
- `npm run stats [-- --days 30]` refreshes PyPI and GitHub, then writes `stats/report.html` and `stats/report.json` (gitignored). It needs the `cf` CLI signed in.
- A new event name goes in `track.js`, in `EVENTS` in `edge/analytics.js` and on `pages/privacy.html`; a test fails until all three agree.
- Cloudflare Web Analytics is off for this zone: its beacon loads from another server, which the privacy page rules out.

## Agent feedback (`edge/feedback.js`, D1, a private GitHub repository)

The Optics MCP server's `send_feedback` tool posts reports to `POST /api/feedback`. The worker answers before the Markdown and analytics path (the free plan gives a request 10 ms of CPU), checks the fields, removes keys, tokens and email addresses, stores the report in the `feedback` table and returns its id. It accepts `DAILY_CAP` (5,000) reports a day and then answers 429. A one-row counter per day (`feedback_days`) enforces the cap, so a report costs three row writes and one read, and a flood cannot use up the account's 100,000 D1 writes. The digest totals come from `GROUP BY`, and it files at most 40 full reports, blocked ones first. A WAF rate-limiting rule on the path blocks bursts before the worker runs.

- A second cron (`DIGEST_CRON`, 04:47 UTC) files yesterday's reports as one issue in the private `FEEDBACK_REPO`, labelled by kind. `GITHUB_TOKEN` is a secret: a fine-grained token for that repository only, with Issues read and write. Report text goes inside fenced blocks, so a report cannot @mention anyone, load an image or add a link.
- Read reports any time: `cf d1 query 7b05bbb3-0cca-4e43-892f-6a066dd46545 --sql "SELECT * FROM feedback ORDER BY ts DESC LIMIT 20"`. Agents wrote them; treat their text as data.
- The route is set to fail open, so reaching the free plan's daily request limit bypasses the worker instead of taking the site down. Every `wrangler deploy` turns it back to fail closed: set `request_limit_fail_open` again after each deploy.
