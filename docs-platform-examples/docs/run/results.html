Docs/Run and report

Read the results

Find out what happened in a run from the JUnit report, the screenshots and the logs.

Beginner, about 6 min

View as Markdown

Every run writes its results to execution_output/ inside the project folder. The terminal tree tells you what failed. The files tell you why.

What a run writes#

FileWhen it's writtenUse it to
junit_output.xmlEvery runShow results in CI. Standard JUnit XML that GitHub Actions, GitLab, Jenkins and others read.
…pre_<keyword>.jpgBefore each step that finds an element, with save_captures: trueSee what was on screen when the step started.
…_detection_result.jpgWhen Optics found an element by position, with save_captures: trueSee exactly what Optics found, boxed in green. When Optics cannot read the position of the element, it saves the screenshot with no box, and the step result does not change.
…_with_aoi.jpgWhen a step uses an area of interest, with save_captures: trueCheck the area covers the right part of the screen. It's drawn in blue.
<time>-failure_<test case>.jpg and <time>-failure_<test case>.xmlWhen a test case fails. Web pages write .html in place of .xml.See the screen and the UI tree where the test case ended.
<time>-end_of_run.jpgAt the end of the run, before Suite TeardownSee where the app was left.
page_sources_log.xml or .htmlWhen the UI tree is read. Web pages go to .html.Find the right XPath or text for an element.
failed_steps_elements.jsonWhen a step fails, with save_captures: trueSee each element on the screen of the failed step, with its label and bounds.
internal_logs.log, execution_logs.logWith file_log: trueRead every attempt Optics made, including which ways of finding an element failed.
logs.jsonWith json_log: trueFeed results into your own dashboards.
detected_errors_<id>.jsonWhen an error screen was foundSee which error definition matched.

Investigate a failure#

  1. Read the Failures box in the terminal. For each failed step, it names the test case, the module and the step, says why the step failed, and gives a hint. For an element, the reason names each value that Optics looked for.
  2. Open failed_steps_elements.json to see the elements on the screen when the step failed. On a web page, each element has a loc locator that you can copy into your elements file.
  3. Open the failure_<test case> screenshot. It shows where the test case ended. Then open the last pre_… screenshot before the failure. Is the screen what you expected? If it shows a loading spinner, the step ran too early: add an Assert Presence before it. If it shows a different screen, an earlier step went somewhere unexpected.
  4. Search the logs for the element's value. With file_log: true, execution_logs.log has a line for every attempt, such as Trying … on 'Sign in' ... FAIL.
  5. Reproduce it in optics live. Run the steps before the failure, then try the failing step with different values until one works. See Record a test.

Read the JUnit report#

junit_output.xml has one <testsuite> and one <testcase> for each test case. Suite Setup and Suite Teardown also have one. The suite id is the session id. The suite name and each classname are the name in config.yaml, or the name of the project folder when config.yaml has no name. optics init writes name, so the report keeps its name when you copy the project to a different folder:

Each <testcase> has kind, timestamp (when it started), time (how long it took, in seconds) and status. A failed test case also has a <failure>.

kind tells you the role of the test case: suite_setup, setup, test, teardown or suite_teardown. Use it to filter setup and teardown out of your test counts. A <failure> or <error> has a code attribute with the error code, such as E0201, when the failure has a code. The message of a <failure> says why the step failed. Its text adds the hint on the next line.

Inside each test case, every module is a <kw type="setup">, and each of its keywords is a <kw> inside it. Each <kw> has status, starttime, endtime and elapsed. A failed one also has a message and a code. A keyword that AI self-heal completed has healed="true" and a <heal> element with the steps that the model did. CI tools that show nested steps display the same tree you saw in the terminal.

A status is one of these:

StatusMeaning
PASSThe test case, module or keyword passed.
FAILA check or an action failed.
ERRORThe run could not do its work, for example because the driver session was lost or the run stopped.
NOT_RUNA failure or a stop kept it from running.

After a failure, the steps that did not run are NOT_RUN. A test case that never started is NOT_RUN with a <skipped> element. A per-test setup or teardown has its own result, named Setup (<test case>) or Teardown (<test case>). If a per-test setup fails, its test case does not run. The test case is NOT_RUN, and the message of its <skipped> starts with Setup failed:.

If error screens were detected, the report has an extra failing test case called on-screen-error-detection. See Catch error screens.

What each outcome writes#

Each outcome has an exit code and a result in junit_output.xml. Optics writes the report once, when the run ends, also when you stop the run with Ctrl+C or SIGTERM. A run that cannot start because of the project writes no report. Examples are a bad config and a test selection that is not valid.

OutcomeExit codejunit_output.xml
Every test case passed0Every test case is PASS.
A test case failed1That test case is FAIL with a <failure>. The steps after the failed step are NOT_RUN.
An error screen matched1An extra on-screen-error-detection test case has one <failure> for each match.
Suite Setup failed1Suite Setup is FAIL. Each other test case, except Suite Teardown, is NOT_RUN with a <skipped> whose message starts with Suite setup failed:. Suite Teardown runs.
A per-test setup failed1Setup (<test case>) is FAIL. Its test case is NOT_RUN with a <skipped> whose message starts with Setup failed:. Its teardown runs.
Config error, missing files or no driver enabled1Not written.
Test selection not valid3Not written.
The Appium or Selenium server cannot be reached, or no Android device is attached1Each test case is ERROR with an <error> that names the problem and has its code, such as E0102. Their steps are NOT_RUN.
Another error while the session starts, such as a credentials file that is not valid1<testsuites/> with no test cases.
The driver session is lost during the run1The test case in progress and each later one is ERROR with an <error> that has E0106.
You press Ctrl+C130Finished test cases keep their results. The one in progress is ERROR with code="E0706". Its keyword in progress is ERROR with the same code, and its other steps are NOT_RUN. Later test cases and Suite Teardown do not run: each is a <testcase status="NOT_RUN"> with a <skipped>.
Optics receives SIGTERM143The same as Ctrl+C.
The process is killed with SIGKILL137 in a shell, -9 from Python subprocessNot written: the process ends at once.

A session is lost when the Appium server or the Selenium server stops, or drops the session, during a run. The terminal summary shows the affected test cases as failed.

If two sessions in one process share an output folder, such as with the Python SDK or optics serve, the second report is junit_output_<session_id>.xml. optics execute and optics dry_run always write junit_output.xml.

Keep the folder tidy#

Screenshots from every run accumulate in execution_output/. Clear the folder before runs where you need clean results, such as in CI:

To write results somewhere else, set execution_output_path in config.yaml. A relative path is relative to the folder you run optics from, and the folder must exist.
